# Sentry → 麦特云主动同步

上传录像中的事件摘要和 SEI 辅助驾驶状态，不上传 MP4，不需要 frp、服务器入站端口或 Sentry 网页密码。
版本 1.1.0 同时上传带时间偏移的挡位、车速、方向盘角度、转向灯和三轴加速度采样。
上传器 1.4.0 起改成「探测 → 窗口内粗扫 → 窗口外补精扫」三级扫描，停车片段不再逐帧全量解析。
云端须先执行配套 `0024_sentry_samples.sql` 迁移并发布新版接口，再升级上传器。
本阶段为 Python 标准库实现，支持 Pi Zero W 的 ARMv6；部署前仍需实机测量解析负载和积压。

## 配套版本与部署顺序

Pi 查看器网页的「设置 → ☁ 麦特云」可粘贴一次性绑定密钥，完成绑定并安装、启动上传服务。
网页必须启用登录保护，查看器需以 root 运行，且本机已有上传器和安装脚本。
密钥只在本次请求中使用，不写入页面或日志；绑定状态只显示是否已绑定和服务是否运行。
已绑定设备不会被覆盖。若云端已接受绑定但本机服务安装失败，设备配置仍保存在
`cloud.json`，可在 Pi 上手动重跑 `sudo sh scripts/install-cloud-sync.sh`。

1. 先把麦特云配套改动应用到 `myteslacloud`，执行 `0023_sentry.sql` 迁移，再发布对应的 Functions 和前端。
2. 在麦特云设置页打开「Sentry 数据同步」，选择车辆和**录像文件名的实际 UTC 偏移**，生成一次性绑定凭据。
3. 在 Pi 的新版 Sentry 源码目录绑定并安装上传服务。

```sh
# 在 Pi 上执行。凭据在交互提示中输入，不放在命令行或 URL。
sudo python3 sentry-cloud-sync.py enroll --server https://www.myteslacloud.com
sudo sh scripts/install-cloud-sync.sh
```

绑定凭据有效期 10 分钟、只能消费一次。设备 Token 仅保存于 Pi 的
`/opt/tesla-sentry/cloud.json`（0600），云端只保存其哈希。
若绑定响应丢失，重新生成绑定凭据；在麦特云撤销可能已创建但未配置的设备。
不同环境使用各自的域名，不要把生产设备绑到临时预览站点。

安装要求 systemd >= 247。安装脚本使用当前源码安装查看器和上传器，
为旧查看器保留 `sentry-viewer.pre-cloud.py`，新增只读 `--cloud-telemetry` 提取命令。
运行中的查看器无需重启，USB Gadget 配置和录像镜像不受此安装步骤影响。
若安装目录自定义，请同时传入对应配置路径和目录：

```sh
sudo python3 sentry-cloud-sync.py enroll --config /your/install/dir/cloud.json
sudo sh scripts/install-cloud-sync.sh /your/install/dir
```

## 运行与诊断

```sh
systemctl status sentry-cloud-sync.service --no-pager
journalctl -u sentry-cloud-sync.service -n 40 --no-pager
sudo python3 /opt/tesla-sentry/sentry-cloud-sync.py status
```

服务使用 systemd 临时用户、受保护的凭据和独立 StateDirectory，降低进程优先级，
限制 CPU 为一个核心的 40%、内存为 160 MB。归档目录及其父目录需要对该用户可读/可遍历；
默认 `/archive` 通常满足，但不要为此放宽密钥文件或整个 `/root` 的权限。
设备状态页显示最后上报时间和待上传片段数；它不是视频实时状态。

队列默认 `/var/lib/tesla-sentry-cloud/queue.sqlite`。上传成功后才清除待传标志；
网络错误指数退避，401/403 等持久错误延后重试，等待期间仍每轮提取新数据。
数据库存储与进程锁阻止两个上传进程并发处理同一队列。
待上传上限为 10000 条 / 64 MB；满时保留已有队列并暂停提取，状态显示 backpressure。
网络长期不可用时，尚未提取就被原录像滚动清理的片段无法恢复。
已确认且源文件已删除的指纹保留七天，定期清理；SQLite 可复用已释放的页面。

停用上传不会删除已上传的数据：

```sh
sudo systemctl disable --now sentry-cloud-sync.service
```

撤销上传权限须在麦特云设置页撤销设备。重新绑定创建新的设备身份，
应使用新的队列数据库，或先归档旧队列；程序会拒绝把旧队列发给另一个设备/服务器。
卸载 Sentry 默认保留本地队列，`--purge` 会一并清除。
新版 systemd 设备支持查看器与上传器整包 OTA，见 [OTA 说明](OTA.md)。
首次账号绑定和服务启用仍需上述安装步骤；旧版迁移需先升级查看器，再补齐组件。

## 扫描策略与成本（上传器 1.5.0）

先按分类决定扫不扫, 再按成本分三层, 保证"该扫的一定扫到, 不该读的一段不读":

| 分类 | 规则 |
| --- | --- |
| `SentryClips` 哨兵告警 | **不解析、不上报**。停车触发、整段没有 SEI, 读视频纯属浪费 |
| `SavedClips` 手动保存 | **一定解析**。不看解析窗口、不受积压影响, 空闲时再补逐帧精扫 |
| `RecentClips` 连续录像 | 只解析最近 30 分钟。窗口内先粗扫, 出窗口后空闲补精扫 |

三层提取成本:

1. **SEI 探测**: 读出 MP4 样本表后, 每 16 帧抽查一帧找特斯拉 SEI, 命中即停。
   整段都抽不到就按 `no_sei` 上报, 不再逐帧全量解析。停车片段基本都是这种情况,
   单段成本从"读完整段视频"降到"读约 6% 数据"。行车片段每帧都带 SEI, 抽查必命中, 代价可忽略。
2. **窗口内粗扫**: 命中 SEI 的片段按 1/4 帧采样(`stride=4`)解析并先上传一版,
   保证解析窗口关闭前一定有一份数据。AP 段的时间分辨率约 150ms, 远小于状态段要求的 500ms 间隔。
3. **窗口外补精扫**: 粗扫结果确有 SEI 的片段, 离开窗口后空闲时再按逐帧(`stride=1`)重扫,
   以更高 revision 覆盖。`no_sei` 的片段不会精扫, 所以停车片段只花一份成本。

扫描顺序: 快过期的 → 手动保存(新片段优先) → 其余窗口内片段(剩余窗口最少优先)。
剩余不足 120 秒时一轮多扫几段(上限 8 段); 一轮里同一精度的片段合并进一次提取进程,
省掉每段重启解释器的开销。精扫只在没有待扫片段时进行, 不和截止任务抢算力。

可调环境变量:

| 变量 | 默认 | 说明 |
| --- | --- | --- |
| `TSF_SEI_PROBE` | `1` | 设为 `0` 关闭探测, 退回逐段全量解析(排障用) |
| `TSF_SEI_PROBE_STRIDE` | `16` | 探测抽样间隔(帧) |
| `TSF_SEI_PROBE_BYTES` | `0` | 探测时每帧只读前 N 字节, 0 表示读整帧 |
| `TSF_CLOUD_FILE_TIMEOUT` | 粗扫 45 / 精扫 120 | 提取器单段硬超时(秒), 超时不拖累同批其它片段 |

查看器的"同步状态"悬浮说明会显示本轮的粗扫段数、精扫段数、超窗不扫段数、待精扫段数、
提取耗时, 以及单个片段的扫描精度; 解析窗口也按分类显示。

## 数据含义

同一组时间戳的多路录像只解析主摄（front）：主摄解析成功即算该组解析完成，即使没有 SEI 也不再看其它路；
只有主摄文件读不出来（损坏或截断）时才回退到下一路。复制完成的正式文件才参与提取，
解析前后校验文件大小和修改时间。内容改变在旧版本确认后形成新 revision。
片段 ID 由归档内分类/目录/时间戳生成，不上报设备绝对文件路径。

- 使用录像文件名作为片段开始时间，按绑定时配置的 UTC 偏移转换成 UTC 毫秒。
- 相邻有效采样间隔最多 500 ms 才能形成状态段，不延长到录像尾部或跨过缺口。
- 保留原始状态：当前沿用查看器 `1=FSD / 2=AP / 3=TACC` 映射。
- 云提取模式下 AP 字段缺失为未知，不能假设为 0；原网页的既有解析行为保持兼容。
- `no_sei` / `no_ap` 不产生任何已知状态区间，不表示未开启辅助驾驶。
- 状态变化时刻受现有解析器的采样间隔和帧时间估算影响，不是精确控制信号。

云提取按每个视频样本读取 SEI（上限沿用解析器的 4000 个样本）。
telemetry.fields 定义采样列，telemetry.samples 保存逐点数据，缺失标量为 null；
文件指纹包含本次提取格式版本，旧队列确认后会对仍在本地的录像生成新版 revision。
已被删除且之前仅上传状态段的录像，无法补出详细采样。每批数据按大小控制在 900 KB 内。

中国通常配置 `480`，但应先对照一段实际录像的文件名、车机时间和行程时间验证。
本阶段使用固定 UTC 偏移，使用夏令时或跨时区后应重新绑定；不会自动猜测历史录像的时区。
不要将含旧时区录像的归档在新偏移下重新提取。

后台返回不同来源的观测，前端对重叠且矛盾的状态显示未知。
设备绑定保存车辆 VIN 快照；当前车辆 VIN 已改变时，不把旧设备数据关联到新车。
没有 VIN 的数据源依赖车主选择正确车辆，车辆更换后必须撤销旧设备并重新绑定。

## 逐片段状态（查看器 2.7.0 / 上传器 1.5.0）

`SentryClips`（哨兵告警）不解析，卡片固定显示「哨兵告警不解析」；`SavedClips`（手动保存）一定解析，
永不判超窗；`RecentClips`（连续录像）只看最近 30 分钟。按文件名时间及设备配置的时区判断，
不按文件复制/修改时间判断。历史录像不补解析，过期的解析失败记录不再重试；
已经解析并进入上传队列的摘要仍正常上传和重试。请确保设备时间和时区正确。

每解析一组录像立即执行上传，不等待其他录像解析；已有待上传摘要连续分批发送。
录像卡片、播放器每路视频和片段切换按钮显示同步状态，只查询屏幕可见的状态，
每 3 秒最多请求一批（75 组）；处理中缓存 3 秒，其他状态缓存 30 秒，上传成功缓存 5 分钟。
重绘页面复用状态缓存，不重新查询全部历史录像；
状态请求超过 10 秒显示获取失败，后续自动重试。
同目录、同时间戳的多路摄像头共用一个片段摘要，标记表示该组遥测的处理和上传状态，
不表示每路视频分别被解析或上传了视频文件。

- 待扫描 / 排队中：队列可读、片段仍在自动解析窗口内，但尚无处理记录。
- 哨兵告警不解析：哨兵触发的停车片段没有 SEI，上传器不读这段视频，云端也不会有它的遥测记录。
- 积压老视频不扫：连续录像的录制时间已早于自动解析窗口（手动保存不受此限），上传器不会补扫；本地录像照常可看可下载。
- 正在解析：上传器已经开始读取该片段的视频。
- 窗口外精扫中：粗扫过的片段离开解析窗口后（手动保存则是空闲时）按逐帧重扫，完成后以更高 revision 覆盖。
- 已解析 · 待上传：摘要已持久保存，尚未收到云端确认。
- 正在上传：正在发送包含该片段的批次。
- 上传成功：云端确认批次 ID、片段 ID 和 revision 后才显示。
- 解析失败 / 上传失败：记录失败类别或 HTTP 状态码，等待自动重试。
- 处理中断：解析/上传记录超过 15 分钟未更新，需检查服务。

积压判定使用上传器写入队列的分类解析窗口与录像时区；旧版上传器没有这些项时只显示“待扫描 / 排队中”，
不臆断为不会再扫。鼠标停留可查看来源视频、状态更新时间、服务最近错误及重试时间。
未初始化队列、权限不足或接口失败会显示状态不可用，不误报排队或成功。
升级前已确认上传的片段可从旧队列恢复成功标记；旧版未记录的解析进度无法追溯。
“上传成功”只表示云端接收摘要，仍可能是 no_sei 或 no_ap；SEI 内容使用诊断页检查。

查看器只读队列公开状态列，不读取 Token 或上传 payload。
默认读取 `/var/lib/tesla-sentry-cloud/queue.sqlite`，自定义队列位置时为查看器配置
`TSF_CLOUD_STATE` 为上传器 `--state` 的相同路径，并确保查看器用户可读数据库与 WAL。
